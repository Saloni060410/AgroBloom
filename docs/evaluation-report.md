# Evaluation report (R-series, PRD §10)

Judge-facing evidence for KhetGPT: model results, formula check, and impact estimate. Every
number below was produced by actually running the real code (`src/models/train.py`,
`src/evaluation/metrics.py`, `src/engine/npk_calculator.py`, `src/engine/recommendation_engine.py`)
against the data and reference tables already in the repo — nothing here is hand-calculated or
invented. Where a number can't be produced honestly (too little real data, a genuine unsourced
gap), that's stated directly instead of guessed.

## 1. Model results

### 1.1 The one number to read first: how much of this is real data

The classifier's test split has **421 rows, of which only 10 are real** (the rest — 411 rows,
97.6% — are synthetic, generated by `generate_synthetic_data.py` from sourced soil-band and
weather tables, not observed farmer behavior). The same skew runs through train (38 real / 1,967
synthetic) and val (9 real / 422 synthetic) — **57 real rows total**, from the 99-row public
Kaggle dataset (`gdabhishek/fertilizer-prediction`) after dropping unusable rows/classes. Every
metric below is measured almost entirely on synthetic, rule-derived data. **Treat every accuracy
number in this section as an upper bound on what the classifier would do on real farmer data, not
a real-world estimate** — this is the single most important limitation of the model, and it does
not go away by adding more synthetic rows.

### 1.5 Worst errors, inspected

From the fresh reproduction's 200 misclassified test rows (out of 421):

1. **Chickpea collapses to "dap" entirely.** Every one of chickpea's 42 misclassified test rows
   (both true `np_20_20_0` and true `np_28_28_0`) was predicted `dap`, regardless of the row's
   actual N/P/K values. This isn't a subtle confusion — it's the model defaulting to one answer
   for an entire crop. Likely cause: chickpea's real feature space in the synthetic data (low N
   requirement — chickpea is a legume, `reference_doses.csv` gives it only 14.8 kg/ha N vs
   wheat's 123.6) looks close enough to dap's typical low-N profile that the model never learned
   to separate it from the NP grades within that crop.
2. **`np_28_28_0` → `urea` is the single largest cross-crop confusion pattern** (15 rows for
   cotton alone, plus smaller counts across maize/rice/sugarcane/barley) — the reverse direction
   also happens (`urea` → `np_28_28_0`/`np_20_20_0`, 10-14 rows per crop). The three products'
   N:P:K compositions genuinely overlap in the mid-range soil values the synthetic generator
   samples from, so this reflects real label ambiguity in the training signal, not an
   implausible model failure.
3. **`urea` → `npk_17_17_17` for sugarcane (10 rows).** `npk_17_17_17` is a thin class (20 rows
   nationally, 3 in the whole test split) — a handful of misclassifications there swings its
   recall a lot; not evidence of a systematic sugarcane-specific problem the way the chickpea
   pattern is.

### 1.6 What this classifier cannot do (stated honestly)

- **It has not been validated on real farmer data at any meaningful scale.** 57 real rows total,
  10 of them in the test split, is not enough to claim the reported accuracy would hold in
  production. This is disclosed in `ml/data/README.md` and `DATA_REQUIREMENTS.md` and repeated
  here because it's the fact that most changes how every other number in this report should be
  read.
- **It doesn't drive the recommendation on its own.** Per `recommendation_engine.py`'s documented
  design, the classifier's product suggestion is secondary to the transparent soil-test-based
  dose calculator (`npk_calculator.py`) — a missing or degraded classifier never blocks
  `/recommend`, and the calculator alone produces a complete, correct, sourced answer. Section 2
  below evaluates that calculator independently.
- **Thin classes stay unreliable regardless of overall accuracy.** `npk_17_17_17` (3 test rows)
  and the excluded `npk_10_26_26` (2 rows total, too few to cross-validate at all — routed to the
  rule-based calculator instead, never asked of the classifier) are both too small to trust a
  learned prediction for; `npk_14_35_14` (the new 6th class, 9 rows) is on the same footing.
- **Chickpea's classifier output should not be trusted** given §1.5's finding — the calculator's
  own dose numbers (§2) are unaffected and remain the source of truth regardless.

## 2. Formula check

### 2.1 Continuous coverage: `test_formula_sanity.py`

The committed, currently-passing regression suite (`ml/tests/test_formula_sanity.py`) already
runs `formula_conformity` over a systematic grid of every crop × soil-rating combination on every
test run (316/316 passing as of this report), using `agronomy_rules.yaml`'s
`formula_tolerance_pct` (10%). This is the authoritative, continuously-enforced check, not a
one-off.

### 2.2 Independent grid run for this report

A separate grid — 7 crops × 3 soil profiles (low/medium/high N, P, K) × irrigated, generic
variety, no prior usage, 63 crop/nutrient checks total — run directly against
`compute_balance()`'s live output and independently cross-checked by `formula_conformity`'s own,
separately-written recomputation from the same reference tables:

**Conformity rate: 54/63 (85.7%). Zero arithmetic mismatches found** (no violator anywhere had
reason `"outside tolerance"` — the only kind that would indicate a real formula bug). All 9
violators are the same disclosed data gap: no sourced `soil_adjustments.csv` row exists yet for
wheat/N, wheat/P, or rice/N (3 soil profiles × 3 crop/nutrient pairs = 9) — exactly the same
`(crop, nutrient)` pairs `test_formula_sanity.py`'s own `_KNOWN_NO_ADJUSTMENT_SOURCE` allow-list
already names. Independently arriving at the identical set of gaps from a separate script is
itself a useful cross-check that the known-gaps list is accurate and complete, not stale.

> **Update, October 2026.** The grid above describes the flat standard dose these three pairs had when it
> was run, and was not re-run. Since then the engine applies the general ICAR soil-test band rule to them
> (low and very low +25%, medium unchanged, high -25%; `agronomy_rules.yaml`, `soil_rating_fallback`), so
> `formula_conformity` still reports them as the same disclosed gap, and it cannot check the banded
> doses. `ml/tests/test_formula_sanity.py::test_band_rule_doses_match_an_independent_recomputation` does:
> it recomputes each from `reference_doses.csv` and the YAML factors, not from the engine.

## 3. Impact estimate

**Every number below is an estimate derived from one specific logged previous-usage pattern for
one specific demo field — never a claimed population-level average.** Labeled as such throughout.

### 3.1 Assumptions, written out

- **Prices:** urea ₹5.92/kg, DAP ₹27.00/kg (IFFCO's own published MRP list, dated 2025-01-01,
  `ml/data/external/fertilizer_products.csv`); MOP ₹34.21/kg (PIB Release ID 2237470, Ministry of
  Chemicals and Fertilizers, "Government Stabilizes Fertilizer Prices for Rabi 2025-26", 10 Mar
  2026 — a government-reported market-average retail price, not one company's MRP list).
- **Area:** each scenario is priced per-acre, matching the field size stated in its own seed data
  (4.5 acres wheat, 3.0 acres rice, 2.5 acres maize) — the reported ₹/acre figures don't depend on
  the field's total size, only its previous-usage pattern.
- **Previous-usage pattern:** each scenario's "previous cost" comes from that field's own logged
  `previous_fertilizer_usage` (real numbers written into the demo fixture, priced at the same
  current rates as the recommendation — never a separately-invented historical price).

| scenario | previous practice | recommended plan | previous cost | recommended cost | saving |
|---|---|---|---|---|---|
| Wheat, over-application | 150 kg/acre urea | 22.4 kg/acre urea | ₹888.00/acre | ₹132.71/acre | **+₹755.29/acre** (85.1% over-application reduction) |
| Rice, low N + rain hold | none logged | 60.9 kg/acre urea, split, delayed 2 days for rain | *null (no baseline — never invented)* | ₹360.58/acre | *null* |
| Maize, healthy field | 100 kg/acre urea + 50 kg/acre DAP (no potash) | 42.2 kg/acre DAP + 20.0 kg/acre MOP + 41.3 kg/acre urea | ₹1,942.00/acre | ₹2,068.33/acre | **−₹126.33/acre** (plan costs more — the field genuinely needed potash the farmer hadn't bought) |

The maize result is intentionally not a "success story" — it's the honest number now that MOP has
a real price (see `ml/SUMMARY_FOR_SALONI.md` §3). A correctly-priced, complete plan can cost more
than an incomplete one; that's the point of showing K2O need explicitly rather than only showing
savings when they're flattering.

### 3.2 What a typical farmer applies today (cited, not invented)

**Source:** Economic Survey 2025-26, Government of India (tabled in Parliament 29 Jan 2026),
as reported by [Down To Earth, 29 Jan 2026](https://www.downtoearth.org.in/agriculture/economic-survey-2026-raise-urea-price-provide-direct-transfers-to-farmers-to-curb-overuse):
India's national N:P:K fertilizer-use ratio worsened from **4:3.2:1** in 2009-10 (close to the
agronomically recommended ~4:2:1) to **10.9:4.1:1** by 2023-24 — i.e., nationally, farmers now
apply roughly 2.7x too much nitrogen relative to phosphorus and potassium compared to the
recommended balance, driven by urea's much larger subsidy relative to P/K fertilizers.

**This is a national-level, directional statistic, not a Punjab-specific or per-acre figure, and
it is not used to derive any number in §3.1** — those come entirely from each demo field's own
logged usage. It's cited here only to establish that the wheat scenario's nitrogen
over-application pattern (§3.1, row 1) is consistent with a real, documented national trend, not
an artificially constructed worst case.
