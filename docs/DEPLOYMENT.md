# Deploying AgroBloom

The default way to run the project is `docker compose` (see the README). This page is for putting it on a public host. Four things run: the website, the backend API, the ML service and a Postgres database.

| Part | What it is | Port | Health check |
|---|---|---|---|
| Website | Static build of `frontend/` | any | `/` |
| Backend | `backend/Dockerfile`, runs migrations on start | `PORT` (default 4000) | `/api/health` |
| ML service | `ml/Dockerfile`, no database | 8001 | `/health` |
| Postgres | Version 16 | 5432 | |

## Option A: Render (blueprint in this repo)

[`render.yaml`](../render.yaml) describes all four parts.

1. Push the branch you want to deploy (normally `main`).
2. In Render choose **New > Blueprint** and pick this repository. Render lists the database and three services.
3. Render asks for the values marked `sync: false`. They are the public URLs of the other services, which do not exist yet, so enter placeholders such as `https://placeholder.invalid` and apply.
4. When the services are up, open each one and set the real values, then redeploy the one you changed:

   | Service | Variable | Value |
   |---|---|---|
   | `agrobloom-api` | `ML_SERVICE_URL` | the `agrobloom-ml` URL, for example `https://agrobloom-ml.onrender.com` |
   | `agrobloom-api` | `CORS_ORIGIN` | the `agrobloom-web` URL, for example `https://agrobloom-web.onrender.com` |
   | `agrobloom-web` | `VITE_API_BASE_URL` | the `agrobloom-api` URL plus `/api` (baked in at build, so redeploy the website) |

   The JWT secrets are generated by Render. `DATABASE_URL` is wired to the database automatically.
5. Check `https://<api>/api/health` and `https://<ml>/health` both answer `ok`, then open the website.

### Demo data on the hosted database

The seed script runs from your computer against the hosted database, because the free plan has no shell. Use the database's **External** connection string from the Render dashboard:

```bash
cd backend
DATABASE_URL="<external connection string>" \
DEMO_FARMER_EMAIL=kisan@khetgpt.in DEMO_FARMER_PASSWORD=password123 \
DEMO_SEED_API_BASE_URL=https://<your-api>.onrender.com \
npm run db:seed:demo
```

The email and password above are what the landing page's **Demo dashboard** button signs in with. To use others, set `VITE_DEMO_EMAIL` and `VITE_DEMO_PASSWORD` on the website service and use the same values here. The demo account is public by design: anyone who opens the site can sign in as it, so keep nothing real in it. `npm run demo:reset` rebuilds it.

## Option B: any host that runs Docker

1. Create a Postgres 16 database and note its connection string.
2. Run the ML image and the backend image (both are plain `docker build` contexts: `ml/` and `backend/`).
3. Give the backend the variables in the table below. It applies the database migrations itself when it starts.
4. Build the website with `VITE_API_BASE_URL=https://<your-api>/api` and `VITE_USE_MOCK=false`, and serve `frontend/dist` from any static host. `frontend/Dockerfile` does this with nginx; `frontend/vercel.json` and `frontend/public/_redirects` make Vercel and Netlify serve `index.html` for client-side routes.

## Environment

| Where | Variable | Notes |
|---|---|---|
| backend | `NODE_ENV=production` | Also makes the backend trust one proxy hop, so rate limits count each visitor |
| backend | `DATABASE_URL` | Postgres connection string |
| backend | `JWT_ACCESS_SECRET`, `JWT_REFRESH_SECRET` | Different random 32-byte values (`openssl rand -hex 32`) |
| backend | `CORS_ORIGIN` | The website's origin, or a comma-separated list |
| backend | `ML_SERVICE_URL` | Where the ML service answers |
| backend | `ML_TIMEOUT_MS` | How long to wait for it (default 5000; the blueprint uses 90000) |
| backend | `WEATHER_SERVICE_URL`, `GEOCODE_SERVICE_URL` | Open-Meteo defaults work, no key |
| ml | `PORT`, `PREDICT_MODE`, `DATA_EXTERNAL_DIR`, `MODEL_ARTIFACT_DIR` | The blueprint sets them |
| website (build time) | `VITE_API_BASE_URL`, `VITE_USE_MOCK=false`, `VITE_API_TIMEOUT_MS` | Vite bakes these into the build |

Never commit a `.env`. The values above go into the host's dashboard.

## Things to know

- **The ML image trains its own classifier.** `ml/models_artifacts/` is git-ignored (the team rule is never to commit model files), so `ml/Dockerfile` trains the rule-imitation classifier while the image is built (a few seconds, same config and seed as a local run) and `/health` reports `ok`. A failed training fails the build, so an image never ships without it. The model is taught to pick the same main product as the rule engine, so it agrees with the plan on about 99% of requests; it adds a side note when it does not and never changes the plan (`ml/MODEL_CARD_RULE_IMITATION.md`). Because it learns the rules, it is retrained on every build and must be retrained locally after a change to `data/external/`. To use a different model, train it locally and mount `models_artifacts/` over the image's, as `docker-compose.yml` does.
- **The ML service is not password protected.** It is stateless and only does arithmetic on the request, but it is reachable by anyone who has its URL. Put it on a private network if your host offers one.
- **Free plans sleep.** Render's free web services stop after about 15 minutes without traffic. The first request after a pause wakes the API (about a minute), and the first plan after that wakes the ML service (another minute), so the first screen after a long pause can take two minutes. The blueprint raises the timeouts for this (`ML_TIMEOUT_MS`, `VITE_API_TIMEOUT_MS`), and the API pokes the ML service as soon as it starts. Later requests take under a second. A free Postgres database is time-limited. Check the host's current terms before relying on it for a demo day, and warm the services first.
- **The default demo credentials ship in the website bundle** (`VITE_DEMO_EMAIL` and `VITE_DEMO_PASSWORD`, falling back to the seeded demo account). Use the seeded demo account only.
- **Weather and geocoding need outbound internet** from the backend. If Open-Meteo is unreachable the backend falls back to cached and then seasonal-average weather instead of failing.

## After a deploy

1. `https://<api>/api/health` and `https://<ml>/health` answer.
2. The website opens and the opening scene plays, then the landing page.
3. **Demo dashboard** opens Overview with three farms.
4. Open a farm, then its plan: a recommendation appears with the three-term working. If it fails, check `ML_SERVICE_URL` and the ML service's `/health` first.
5. Reload on a deep link such as `/fields/<id>/schedule`: it loads, it does not 404.
